## 第 1 則（導師）

我把 `pricing.py`、`config.py`、`pipeline.py` 都讀過了。定價的核心在 `pricing.py` 的 `price()`。先給你一個心智模型，再跑一個例子讓它落地。

## 四個步驟，順序是刻意的（`pricing.py:48-69`）

1. **商品小計** `subtotal` = Σ(數量 × 單價) —— 單價來自 **reservation 快照**，不是原始訂單（`:49`）
2. **選折扣**：最多一條，不疊加
3. **稅** = 折扣後金額 × 5%
4. **運費**：達門檻免運，否則收 flat $120；最後把三者相加

## 關鍵：三件事各自看「哪一個小計」

這是最容易搞錯、也是三者互動的真正核心：

| 決策 | 看的基準 | 出處 |
|---|---|---|
| 折扣金額 | 折扣**前** subtotal | `:52` |
| 稅 | 折扣**後** discounted | `:55` |
| 免運資格 | 折扣**前** subtotal | `:57` |

注意**稅和免運看的是不同的數字**。稅吃折扣後（折扣順便幫你少繳稅），但免運看折扣前——所以折扣再多，也不會害你掉出免運門檻。模組 docstring 的規則 4（`:11-13`）就明講：「The discount does not change shipping eligibility.」

另外，**運費永遠不課稅**：稅只算在商品上，運費是最後才加上去、不進稅基。

## 折扣怎麼選（`_select_discount`, `:72-78`）

把所有「小計 ≥ 門檻」的規則挑出來，取 **priority 最高**那條——不是折最多那條。目前兩條：

- `loyalty-10`：10%，門檻 $0，priority 10
- `spring-30`：30%，門檻 $5000，priority 20

因為 loyalty 門檻是 $0，**每張單至少吃 10%**；小計到 $5000 以上，spring-30 用更高 priority 勝出 → 30%。（這裡 priority 高剛好也折最多，但程式是照 priority 選的，不是照金額——這是個潛在的坑。）

## 跑一個例子：小計 $8500

- **折扣**：8500 ≥ 5000 → spring-30 三成 → 折 $2550 → 折後 **$5950**
- **免運**：看折扣前的 $8500 ≥ $8000 → **免運** ✅（就算折後只剩 $5950 也不受影響）
- **稅**：$5950 × 5% = **$297.50**
- **總計**：5950 + 297.5 + 0 = **$6247.50**

如果免運誤用折扣後的 $5950（< $8000），就會被多收 $120——「兩個小計」的設計正是要避免這件事。

## 第 7 則（導師）

完全正確 ✅ 免運看折扣前(9000 一定免運)、稅對折後 6300 算 = 315、總計 6615——之前滑掉的兩點你都扳回來了,這次是真的內化了。

**你的問題:兩條門檻都滿足時,選 priority 最高那條,不會兩個都套。**

看 `_select_discount`(`pricing.py:72-78`):
```python
applicable = [r for r in DISCOUNT_RULES if subtotal_cents >= r.min_subtotal_cents]
if not applicable:
    return None
return max(applicable, key=lambda rule: rule.priority)
```
兩步:先挑出「門檻有過」的所有規則,再用 `max(..., key=priority)` **只回傳一條**。回到 `price()` 的 `discount = subtotal * rule.percent // 100`——就這一條,不累加。所以小計 ≥ $5000 時,spring-30(priority 20)贏過 loyalty-10(priority 10)→ 30%,loyalty 被忽略,不是 40%。

**但有個要小心的點:它選的是 `priority`,不是「折最多」。**

目前這兩條剛好一致——spring-30 priority 高、折也多,所以你看不出差別。但那是巧合,不是保證。假設哪天有人加一條:
```python
DiscountRule("vip-5", percent=5, min_subtotal_cents=0, priority=99)
```
priority 99 最高 → **每一單都套這條 5%**,連 spring-30 的 30% 都被壓掉。系統照樣「正確」執行,因為它只認 priority。「加了新規則反而讓客人變貴」這種坑,就是從 **priority ≠ 划算度** 來的。

**兩個順帶的細節:**
- loyalty-10 門檻 $0 → 永遠成立,所以 `applicable` 不會空,`return None` 實務上跑不到。換句話說**每張單至少 10%**,$5000 以上才「換成」30%(取代,不是相加)。
- 萬一兩條 priority 相同,`max` 會回傳 tuple 裡**排前面**那條(Python `max` 取第一個最大值),於是 `DISCOUNT_RULES` 的排列順序就變成隱性 tiebreak。目前 20≠10 碰不到,但加規則時要記得。
