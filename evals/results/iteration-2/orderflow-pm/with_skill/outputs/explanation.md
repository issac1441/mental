## 直接的答案

這個訂單系統把每張訂單推過四個固定步驟：**收單驗證 → 保留庫存並鎖定單價 → 計價 → 出貨**（`pipeline.py:4`）。每張訂單最後一定落在三種結果之一——**成功出貨**、**直接失敗**、或**進入待處理佇列**（`pipeline.py:31`）。對客戶最關鍵的兩件事：**出貨**若因物流商臨時出狀況而失敗，系統會在約一秒內自動重試 3 次，再不行就把訂單「停」在待處理佇列等人工處理——訂單不會憑空消失，但系統本身**不會自動通知客戶**；**價格**在「保留庫存」那一刻就鎖定，唯一會變動的情況，是同一張訂單隔了**超過 2 分鐘**又被重新處理，這時會照最新目錄價重算。

## 這個系統在做什麼

先建立一張地圖。一張訂單進來後：

1. **收單驗證**（`ingest.py`）：檢查訂單有沒有編號、地區是不是 `domestic`/`offshore`、每個品項有沒有 SKU 與正整數數量。
2. **保留庫存並鎖定單價**（`inventory.py`）：從目錄扣下庫存，同時把**當下的單價「拍照存檔」**進這筆保留。
3. **計價**（`pricing.py`）：折扣、稅、運費都**根據那張保留的價格快照**算，不是根據客戶原本下單看到的價。
4. **出貨**（`dispatch.py`）：挑物流商，把包裹交出去，失敗會重試。

三種結果對客戶的意義：

| 結果 | 何時發生 | 客戶端的實際處境 |
|---|---|---|
| **成功出貨** `dispatched` | 四步都過 | 訂單成立，收據帶著物流商與總金額 |
| **直接失敗** `failed` | 資料錯／SKU 不存在／庫存不足 | 當場退回，**不重試**（`inventory.py:99-105`, `errors.py:20-29`） |
| **待處理佇列** `dead_lettered` | 物流商連續 3 次出狀況 | 訂單被「停住」等人工，庫存已退回（`pipeline.py:59-67`） |

一個對客戶的重要保護：**2 分鐘內重複送同一張訂單只算一次**，拿到同一筆保留、同一個價格，不會重複扣庫存、也不會重複出貨（`inventory.py:64-67`）。

## 出貨失敗時，客戶會遇到什麼

要先分清楚「失敗」有兩種，客戶的處境完全不同。

**一、當場退回（`failed`）** — 這其實是在出貨「之前」就被擋下：訂單資料有誤、SKU 不存在、或**庫存不足**。系統判定這類問題重試也沒用，所以**立刻回失敗、完全不重試**。要注意一個對客服很實際的細節：多品項訂單只要**一項**庫存不足，**整張訂單都不會保留**（不會出現「保留一半」的狀況，`inventory.py:93-106`）。客戶的體驗是：下單當下就被拒，通常需要改單或補貨。

**二、停進待處理佇列（`dead_lettered`）** — 這才是題目講的「出貨失敗」。當物流商 API 逾時或暫時掛掉（transient，可重試的錯），系統會：

1. 自動重試，最多 **3 次**，間隔逐次加倍（第 2 次前等約 0.2 秒、第 3 次前約 0.4 秒，`dispatch.py:44-63`, `config.py:9`）；
2. 3 次都失敗，就把訂單**「dead-letter（死信）」= 停進待處理佇列**：**把保留的庫存退回**、在佇列記一筆（訂單編號＋原因）、回一張 `dead_lettered` 收據——**而不是讓程式崩潰**（`pipeline.py:59-67`）。程式碼特別註明「絕不默默丟掉訂單」（`dispatch.py:5-7`）。

客戶端的實際處境，有三個你該知道的重點：

- **訂單沒完成、但也沒不見**：它被安全地停下來，等人來救。
- **系統不會自己回頭重試**：整個重試在**約一秒內**就結束了，不是拖幾小時慢慢試。之後要不要重新出貨，得靠這個 repo **以外**的機制。
- **系統不會通知客戶、不會退款**：待處理佇列只是一個「停車場」——記下 `order_id` 和原因（`pipeline.py:62-67`）。通知、退款、重新派送都不在這段程式裡。所以從客戶角度，如果沒有下游流程接手，他會看到訂單卡在「處理中」而沒有下文。

## 價格變動時，客戶會遇到什麼

這是這套系統設計得最細、也最容易誤會的地方。核心規則一句話：**價格以「保留那一刻」為準，之後目錄漲跌都不影響已保留的訂單**（`pricing.py:1-14`, `inventory.py:1-9`）。

**價格為什麼通常是穩的**：保留庫存時，系統把每個品項的當下單價「拍照存檔」進保留；後面計價一律用這張快照。所以就算目錄價在保留後改了，客戶**還是按保留時的價格結帳**。

**價格什麼時候會變**：保留有「有效期限」——**2 分鐘**（`RESERVATION_TTL_SECONDS`, `config.py:4`）。如果**同一張訂單**在超過 2 分鐘後又被重新處理（例如卡住的訂單被重跑），這筆保留會**用當下最新目錄價重建**，計價自然照新價走。程式註解明講：這種「過期重建後的重算」是**合法的、可以在出貨前改變報價的**（`pipeline.py:2-7`, `inventory.py:64-70`）。價格可能因此**變高或變低**。

計價的幾條規則，決定了「價格變動」對客戶的放大效果：

- **每張訂單一定至少打 9 折**：`loyalty-10`（10% off）門檻是 0 元、且程式**沒有檢查會員身份**，所以對所有訂單都成立（`pricing.py:33`, `72-78`）。
- **商品小計滿 5000 元改打 7 折**：`spring-30`（30% off）優先權較高，會**取代** loyalty-10；兩者**不疊加，只取一個**（`pricing.py:32-35`）。
- **稅 5%**，只對「折扣後」商品小計課；**運費不課稅**（`pricing.py:55`, `config.py:12`）。
- **免運看「折扣前」商品小計是否滿 8000 元**，否則固定運費 **120 元**；折扣不影響免運資格（`pricing.py:57-60`, `test_pipeline.py:32-39`）。

把這些放在一起，會出現一個**反直覺、但很真實**的客戶體驗。看一個具體例子：

> 某訂單第一次保留時商品小計 5200 元 → 觸發 7 折。訂單卡住、2 分鐘後被重跑，此時目錄**降價**讓小計掉到 4800 元 → 低於 5000 門檻，折扣**掉回 9 折**。結果是：**牌價明明降了，客戶要付的總額反而可能變高**，因為他失去了那個 30% 的大折扣。

同理，一次重算若讓「折扣前小計」跌破 8000 元，原本免運的訂單會**冒出 120 元運費**。這些都是「價格變動」時，客戶端可能突然看到總額跳動的真正原因。

（對照happy path 好抓感覺：3 個 WIDGET、每個 3000 元 → 小計 9000 → 7 折 6300 → 稅 315 → 折扣前滿 8000 免運 → 總計 **6615 元**，`test_pipeline.py:22-30`。）

## 幾個容易誤會、值得你確認的地方

這些不是 bug 判定，而是「程式現在的實際行為」與 PM 直覺常有落差之處：

- **重算是「無聲的」**：收據只帶新的總金額，**沒有任何欄位標示「這是重算過、和原報價不同」**；pipeline 也沒有把「需重算」的旗標拿去通知任何人（`pipeline.py:69-74`, `inventory.py:69-70`）。若你希望客戶或客服知道價格變了，得另外加。
- **「loyalty-10」其實人人有份**：名字叫忠誠折扣，但沒有會員判斷，等於**全站無條件 9 折起跳**。若商業意圖不是這樣，值得確認。
- **「spring-30」只看金額、不看日期**：名字像季節促銷，但程式**沒有時間窗**，只要小計滿 5000 就一直有效（`pricing.py:32-35`）。
- **待處理佇列之後怎麼辦，不在這裡**：重試上限只有 3 次、約一秒內結束（`config.py:7,9`）；後續的重新派送、退款、通知都仰賴這個 repo 以外的流程。
- **這整段是「內部處理」，沒有任何通知客戶的程式**：出貨那步是把包裹交給**物流商**，不是通知客戶（`dispatch.py:65`）。客戶實際看到的狀態頁／通知信是另一層，不在這份程式裡。
- **順帶一提出貨方式**（影響時效、不影響價格）：離島訂單一律**空運**；本島看重量，**2 公斤以內走 post、超過走 freight**（`dispatch.py:36-41`, `config.py:22`）。
- **過期重跑也可能從「本來會成功」變「失敗」**：重建保留時若庫存已被別人買走，會直接回 `failed`——所以一張卡很久的舊訂單被重跑，結局不保證跟當初一樣。
