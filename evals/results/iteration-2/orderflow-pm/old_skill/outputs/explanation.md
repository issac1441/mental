`orderflow` 是一條內部的訂單處理流水線。每一張訂單會依序經過四關——**收單驗證 → 保留庫存並鎖定單價 → 計價 → 出貨**（`pipeline.py:44`），最後一定會拿到三種結果收據其中之一：`dispatched`（已出貨）、`failed`（當場失敗）、`dead_lettered`（轉人工處理）。

先給你兩個情況的直接答案：

- **出貨失敗**分兩種。訂單「本身」有問題（資料錯、商品不存在、庫存不夠）會**立刻失敗**、附上原因、不重試；訂單沒問題但「貨運商臨時叫不到車」，系統會**重試 3 次**，還是不行就轉成 `dead_lettered`——**訂單不會消失、已保留的庫存會退回**，等營運人工處理。
- **價格變動**的根源是：客戶被收的單價，是在「保留庫存」那一刻拍下的快照，這個快照只鎖 **2 分鐘**。2 分鐘內同一張訂單重跑價格不變；超過 2 分鐘後才重跑，就會用「當下的目錄價」重新計算，客戶的總額因此可能改變。

## 一張訂單怎麼跑完全程

把四關想成一條輸送帶（`pipeline.py:44`–`74`）：

1. **收單驗證**（`ingest.py`）：檢查訂單有沒有編號、地區是不是 `domestic`/`offshore`、每一行有沒有商品代號、數量是不是正整數。任何一項不對 → 收據 `failed`。
2. **保留庫存 + 鎖定單價**（`inventory.py`）：從目錄扣下要的庫存，同時把**當下的單價拍成快照**存進這張訂單的 reservation。庫存不夠或商品代號不存在 → `failed`。
3. **計價**（`pricing.py`）：**一律用上一步 reservation 裡的單價快照**來算，不是用客戶下單當下的原始資料。
4. **出貨**（`dispatch.py`）：挑貨運商、把包裹交出去。這裡才會發生「重試」。

三種收據對客戶/營運的意義：

| 收據 | 意思 | 可否救回 |
|---|---|---|
| `dispatched` | 已成功交給貨運商 | — |
| `failed` | 訂單本身不成立（資料/商品/庫存問題），重試也沒用 | 需客戶或營運修正訂單本身 |
| `dead_lettered` | 訂單成立，但貨運商暫時聯絡不上 | **可救回**：庫存已退回、訂單進待處理佇列 |

## 出貨失敗：客戶會遇到的兩種情況

**情況 A — 還沒到貨運商就失敗（當場、不重試）**
發生在第 1、2 關。觸發原因是「非暫時性」的問題（`errors.py` 裡的 `FatalError` 家族）：資料不合格、商品代號不在目錄、庫存不足。客戶會**立刻**拿到 `failed` 收據並附原因（例如 `ANVIL: want 5, have 2`）。因為重試也不會變好，系統不浪費時間重試（`pipeline.py:46`–`54`）。

**情況 B — 交給貨運商時叫不到車（重試後轉人工）**
發生在第 4 關，觸發原因是「暫時性」問題：貨運商逾時（`CarrierTimeout`）或暫時不可用（`CarrierUnavailable`）。流程是（`dispatch.py:61`–`71`）：

- 最多嘗試 **3 次**（`MAX_DISPATCH_ATTEMPTS`，`config.py:6`）。
- 每次間隔會加倍：第二次前約等 **0.2 秒**、第三次前約 **0.4 秒**，再加上每張訂單固定的一點點抖動（0–0.1 秒）。
- 這 3 次是在同一次處理裡同步跑完的，所以客戶大約**一秒內**就會有最終結果。
- 3 次都失敗 → 系統做三件事：**把庫存退回目錄、把訂單放進 dead-letter（待處理）佇列、回一張 `dead_lettered` 收據**（`pipeline.py:59`–`67`）。

實際例子（來自測試 `test_pipeline.py:51`）：一張 2 件 ANVIL 的訂單，貨運商每次都逾時 → 收據變 `dead_lettered`，而且 ANVIL 的庫存從被扣掉又**退回成 2**。這證明「出貨失敗不等於庫存被卡死或訂單消失」。

**給你的判讀原則**：`failed` = 這張訂單需要有人去改（改資料、補庫存）；`dead_lettered` = 訂單沒問題，是貨運端暫時出狀況，通常重送就能救回。

## 價格為什麼、什麼時候會變

客戶被收的價格 = 用 reservation 裡的**單價快照**算出來的（`pricing.py:48`）。什麼時候這個快照會被換成新的、造成價格變動？關鍵在 reservation 有「同單去重 + 2 分鐘有效期」的設計（`inventory.py:54`–`75`）:

- **2 分鐘內**重跑同一張訂單編號 → 直接拿回**原本那個** reservation → 價格**完全不變**（這叫 idempotent，同一張單處理幾次結果都一樣）。
- **超過 2 分鐘**（`RESERVATION_TTL_SECONDS = 120`，`config.py:4`）後再重跑 → 舊 reservation 過期 → 系統用**當下目錄價**重建一個新的 → 若這段期間商品調過價，**客戶總額就跟著變**。系統會在這個重建的 reservation 上標記 `reprice_required`。

所以「價格變動」通常不是同一次結帳中途變，而是發生在**同一張訂單被延後重跑**時（例如上游系統重送、或當機後補處理），而且中間隔超過 2 分鐘、目錄又剛好調價。這是設計上「合法」的重新報價（`pipeline.py:1`–`14` 的說明就是這個意思）。

**順帶說明總額怎麼組成**，這樣你能自己推算客戶帳單（`pricing.py:48`–`69`，金額系統內部以「分」儲存，這裡換算成元）：

1. 商品小計 = 各行「數量 × 快照單價」。
2. 折扣：**最多套一個**，符合條件的規則裡優先級最高的那個。目前設定下，滿 $5,000 的 `spring-30`（打七折）優先於人人都有的 `loyalty-10`（打九折）。**折扣不疊加**。
3. 稅：對「折扣後的商品金額」課 5%（`TAX_RATE`），**運費不課稅**。
4. 運費：達免運門檻就免，否則收固定 $120（`FLAT_SHIPPING_CENTS`）。

這裡有一條**容易產生客訴/客服疑問的規則**：免運看的是**折扣前**的商品小計是否達到 $8,000（`FREE_SHIPPING_THRESHOLD_CENTS`），不是折扣後。實例（測試 `test_pipeline.py:22`）：3 件 WIDGET，小計 $9,000 → 打七折剩 $6,300 → 加 5% 稅 $315 → 運費因為「折扣前 $9,000 已達門檻」而免 → 總額 **$6,615**。也就是說，折扣把金額壓到 $8,000 以下，**不會害客戶失去免運**。

## 營運上要留意的三個邊界

這幾點是「容易被想當然、但實際不是那樣」的地方，值得你和工程確認：

- **價格變動目前是「靜默自動」的，沒有告知關卡。** `reprice_required` 這個標記雖然會被設上，但 pipeline 從頭到尾**沒有讀它、也沒有因它做任何事**（例如通知客戶「你的價格變了」）。重新報價之所以生效，只是因為計價一律讀最新快照。若產品上希望「價格一旦變動要先告知客戶或攔下來人工確認再出貨」，**目前程式沒有這道關卡**。[observed]

- **過期重建可能把同一張訂單的庫存扣兩次。** reservation 過期重建時，程式是「直接重扣一次庫存」，並**沒有先把舊的保留庫存退回**（`inventory.py:66`–`71`，而退回動作 `release` 目前只在 dead-letter 那條路徑被呼叫）。結果是同一張訂單在過期重跑後，庫存帳面可能被多扣，造成「明明有貨卻顯示缺貨」的幽靈缺貨。這看起來像非預期行為，**建議請工程確認**。[observed 行為 / inferred 風險]

- **「優雅地轉人工」只涵蓋暫時性的貨運商問題。** 系統保證「不會默默弄丟訂單」的前提，是出貨階段丟出的是**可重試**的錯誤。如果出貨時冒出的是非重試類的意外錯誤，目前不會被包成收據（會直接往外拋出例外），這種情況下庫存也不會退回。正常的貨運逾時/暫時不可用不受影響，但這是保護網的邊界。[observed]
